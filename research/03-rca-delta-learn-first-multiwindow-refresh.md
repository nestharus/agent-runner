# RCA: pathological delta on first multi-window refresh

## Root cause
The shipped `upsert_quota_refresh` code does **not** learn a delta for a brand-new `window_id`; it only learns when a prior row with the **same** `window_id` already exists. That means the pathological `last_delta_percent = 1.0` was not created by “new window 1 diffed against old window 0”. The actual condition is: a prior `window_id = 1` row already existed, a later refresh brought in `w.used_percent = 1.0` for that same row, and `count_assistant_turns_since(provider_name, prior.refreshed_at)` returned a small positive count such as `19` or `38`. The code then wrote both `used_percent = 1.0` and `last_delta_percent = 1.0` from that same incoming sample. After that, later refreshes that showed a reset or no increase carried the bad learned delta forward unchanged, which explains the `codex2` shape `used_percent = 0.02, last_delta_percent = 1.0`. Evidence: migration only seeds `window_id = 0`; missing prior window rows take the `None => (None, None)` branch; learned deltas are only written from `w.used_percent - prior_w.used_percent`; later resets/no-change preserve the prior delta pair. `src-tauri/src/state/db.rs:369-374`, `src-tauri/src/state/db.rs:1319-1322`, `src-tauri/src/state/db.rs:1351-1375`

## Evidence
- Migration from pre-multi-window state can only create `window_id = 0`; there is no path here that fabricates an initial `window_id = 1` row. `src-tauri/src/state/db.rs:369-374`
- Window rows are read ordered by `window_id`, then re-matched through a `HashMap<u32, &QuotaWindow>` keyed by the same `window_id`; this is not positional fallback to prior index 0. `src-tauri/src/state/db.rs:1202-1240`, `src-tauri/src/state/db.rs:1319-1322`
- The learning branch is exact: `dp = (w.used_percent - prior_w.used_percent).max(0.0)`, and a new delta is written only when `dp > 0.0 && turns_between_refreshes > 0`. Otherwise the old delta pair is carried forward. `src-tauri/src/state/db.rs:1352-1359`
- A missing prior row for that `window_id` yields `None => (None, None)`. So a truly first-time `window_id = 1` refresh cannot write `last_delta_percent = 1.0`. `src-tauri/src/state/db.rs:1360-1362`
- The same insert statement writes the current row’s `used_percent` and the learned delta pair. So `used_percent = 1.0` on a window row and `last_delta_percent = 1.0` can come from the same refresh payload, but only the delta needs prior same-window state. `src-tauri/src/state/db.rs:1363-1375`
- `turns_between_refreshes` is provider-level, not window-level. It is the count of assistant turns with `timestamp > refreshed_at` since the previous successful refresh. That is exactly where the observed `19` / `38` come from. `src-tauri/src/state/db.rs:1312-1318`, `src-tauri/src/state/db.rs:1964-1991`
- `chatgpt-usage` emits weekly first, 5-hour second, so `window_id = 1` for Codex-family providers is the short 5-hour window. `scripts/chatgpt-usage:47-57`

## Worked example reproducing the bug
1. Pre-hotfix / PR2 migration leaves Codex with only `window_id = 0` copied from legacy `provider_quotas`. There is no `window_id = 1` yet. `src-tauri/src/state/db.rs:369-374`
2. The first successful two-window refresh after the hotfix cannot learn any delta for `window_id = 1`, because `prior_windows_by_id.get(&1)` is missing and the branch is `None => (None, None)`. It can create the row, but not `last_delta_percent = 1.0`. `src-tauri/src/state/db.rs:1351-1362`
3. A later successful two-window refresh for `codex` arrives after `19` assistant turns have been ingested since the previous refresh. That `19` is produced by `count_assistant_turns_since("codex", prior.refreshed_at)`. `src-tauri/src/state/db.rs:1312-1318`, `src-tauri/src/state/db.rs:1964-1991`
4. If the prior short-window row was `window_id = 1, used_percent = 0.0` and the incoming short-window sample is `window_id = 1, used_percent = 1.0`, then `dp = (1.0 - 0.0).max(0.0) = 1.0`. Because `turns_between_refreshes = 19 > 0`, the learner writes `last_delta_percent = 1.0, last_delta_calls = 19`. The same insert also writes the current row `used_percent = 1.0`. `src-tauri/src/state/db.rs:1353-1357`, `src-tauri/src/state/db.rs:1368-1375`
5. That yields the exact codex shape you observed: `window_id = 1, used_percent = 1.0, last_delta_percent = 1.0, last_delta_calls = 19`.
6. `codex2` proves the same bad learn persisted across another refresh: its current `used_percent = 0.02` but `last_delta_percent = 1.0`. Under this code, that can only happen if an **earlier** refresh learned `1.0/38`, and a later refresh saw `dp <= 0.0` and took the carry-forward branch. `src-tauri/src/state/db.rs:1354-1359`

## Why claude2 didn't hit this
There is no provider-specific branch in the learner. `claude2` ran through the same code, but its short-window history apparently never included the pathological “prior short window low, next short window jumps to 1.0” sample. Its observed `last_delta_percent = 0.21, last_delta_calls = 444` is exactly the normal positive-delta branch: prior same-window row existed, the new `used_percent` increased by `0.21`, and there were `444` assistant turns since `refreshed_at`. The differential is therefore in the input sample sequence from the quota refreshes, not in a Codex-vs-Claude code path. `src-tauri/src/state/db.rs:1352-1359`, `src-tauri/src/state/db.rs:1964-1991`

## Scope of damage
At-risk providers are any providers whose quota script reports multiple windows by stable position and whose short-window sample can transiently spike high after a prior same-slot row already exists. The bad sample is amplified twice: first by learning `dp / calls` from a provider-level turn count that may be small, then by carrying that delta forward across later resets/no-change. In the wild, look for `provider_quota_windows` rows where:
- `last_delta_percent` is implausibly large for a short window, especially near `1.0`
- `last_delta_calls` is small
- current `used_percent` is low but `last_delta_percent` remains very high, which signals carry-forward from an earlier bad learn
- pool peers on the same `window_id` have learned rates orders of magnitude lower

The separate `used_percent = 1.0` anomaly on `codex` window 1 is related but not identical. It uses the same incoming `w.used_percent` value that fed the delta learn, but it is written unconditionally from the refresh payload; the delta pathology requires prior same-window state in addition to the bad payload. So the bad `used_percent` write is an upstream sample/order problem, while the persistent user-blocking state came from the learner amplifying and then preserving that sample. `src-tauri/src/state/db.rs:1324-1341`, `src-tauri/src/state/db.rs:1353-1375`
