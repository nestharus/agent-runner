Verdict: LOW

The proposal targets the underlying purpose — actual runtime fanout for both RC-1 and RC-2 — rather than rewiring the harnesses or narrowing the staleness detector to fit the fixture.

**A. Behavior fix, not test-shaped.** Both algorithm changes land in production code paths that `run_with_balancing` and the interactive CLI path traverse, not in harness wiring. The topology probe is described as a new pass inserted into `balancer::select_provider` between the existing stale-refresh/session-scan loop and the exhausted/density branch (proposal §Design Fix-1, lines 17, 21; targeting `src-tauri/src/balancer/mod.rs:98`-`168`). The fanout selector replaces the final argmax line in `score_by_density` (proposal §Design Fix-2, lines 28-37; targeting `src-tauri/src/balancer/mod.rs:170`-`198` and `src-tauri/src/balancer/mod.rs:438`-`454`). Both CLI paths construct `BalanceContext` and call `select_provider` (proposal §Supported-surface, lines 112-113; `src-tauri/src/main.rs:1582`-`1649`, `src-tauri/src/main.rs:1967`-`2101`), so the fix is reachable at runtime — not just in the synthetic harness.

**B. Fanout that actually fans out on the RC-2 fixture.** The selector is "lowest lifetime invocation count → higher score → lower index" within a `binding_score >= best/2.0` band (proposal §Design Fix-2, lines 29-31). With the RC-2 seeds (codex 1.85, codex2 1.28; ratio ≈1.45 < 2.0) both providers enter the band, and because `record_successful_invocation` updates the same `providers` aggregate `get_provider` reads (proposal lines 30, 35; harness loop at `src-tauri/tests/routing_fanout_rca/rc2_argmax_concentration.rs:17`-`23`), repeated selections alternate accounts as counts diverge. There is no 0.001-epsilon dodge or hidden hard-pin — `FANOUT_SCORE_BAND_RATIO = 2.0` is exact (proposal line 31), and AC-2's "within ~2x" requirement is encoded directly (`plans/tickets/phase-11/WU-11-01.md:53`-`57`).

**C. Topology-shrink staleness, not just TTL.** `is_topology_probe_due` is sibling-aware: `pool_expected_live_windows = max(current live-window count, topology_peak_live_window_count)` taken across the model's providers, then probe when a provider's live-window count is positive but below that pool expected (proposal §Design Fix-1, lines 17, 19). For the RC-1 seed (claude=1 window, claude2/claude3=2 windows; `src-tauri/tests/routing_fanout_rca/rc1_incomplete_quota_topology.rs:14`-`16`) pool_expected = 2 > claude's 1, so claude is probed via the supplied two-window script (line 18). This addresses the exact blind spot the RCA names — `is_stale` being provider-local with no sibling comparison or peak memory (`research/11-routing-fanout-rca.md:23`-`36`; `src-tauri/src/quota/mod.rs:183`-`217`) — instead of leaving it intact and adding a TTL knob. The cooldown (`TOPOLOGY_PROBE_COOLDOWN_SECS = 60*60`, line 20) is a blast-radius bound, not a way to suppress probing for the harness fixture; harness rows can leave `last_topology_probe_at` NULL and still get probed (proposal lines 25, 87).

**D. Determinism without losing fanout.** No RNG anywhere; fanout reduces to a pure function of binding scores, existing `providers.invocation_count` aggregates, and provider declaration order (proposal §Design Fix-2, line 37). The proposal explicitly rejects "weighted or stochastic fanout" by name (line 44), and the alternative considered does not collapse the problem to argmax-with-tiebreaker — count-balanced selection is the actual mechanism that distributes traffic.

**E. No "test the absence of bug" trick.** The reproduction harnesses are explicitly kept and unmodified (proposal §Anti-scope line 98; AC-1/AC-2 binding via the existing tests, table rows at proposal lines 141-142). The new inline tests cover distinct properties — hard-pin preservation when the gap exceeds the band (line 145), tiebreaker behavior (line 144), cooldown gating (line 147), migration column presence (line 150) — not duplicate harness invariants. AC-1/AC-2 ride on the existing harness assertions.

**F. Anti-scope used as a constraint, not as cover.** IPC shape, `QuotaWindow.used_percent` naming, and Initiative-B services are left alone (proposal §Anti-scope, lines 93-100). The topology metadata path threads through new `provider_quotas` columns (`topology_peak_live_window_count`, `last_topology_probe_at`) plus an additive migration via the existing `ensure_*_schema` pattern (proposal §Schema-and-migration, lines 49-87; `src-tauri/src/state/db.rs:520`-`538`, `src-tauri/src/state/db.rs:666`-`668`), which the ticket Code Boundary explicitly permits ("potential new column for peak topology / topology hash"). The proposal does not invoke anti-scope to avoid solving RC-1.

**Residual sub-risks (notable but not shortcut-class).**

- Fanout depends on the harness's `record_successful_invocation` updating the same `providers` aggregate that `get_provider` reads. The proposal is explicit about this (assumption A4, lines 132; data-flow line 35), but if the impl agent finds the shared shim writes a different table than `get_provider`'s read path, fanout won't distribute even with correct selector logic. This is verifiable at Phase 6 against the RC-2 GREEN result, not a defeat of purpose.
- The legacy-row backfill of `topology_peak_live_window_count` from the current cached window count (proposal lines 76-87) cannot reconstruct historical peaks. The proposal acknowledges this and relies on the sibling-triggered branch to repair pre-fix one-window rows when at least one sibling exposes the richer topology. Pools where every account has been cached in the shrunken state simultaneously would remain blind until at least one upstream returns its full topology — but RC-1 specifically encodes the sibling-asymmetric case, so the harness contract is satisfied and the assumption is named.

Neither sub-risk reaches MEDIUM: both are acknowledged in the assumption register and have observable signals that the impl/test phases can exercise.
