PR-F does not read to me as a V16 violation. It is one end-to-end concern: "resume an interactive `repl` session by bare UUID, across providers, with observable provenance and correct trace semantics." The diff spans config, DB, executor, CLI, and trace because that concern crosses those layers. Most of the listed pieces are not independently shippable features; they are load-bearing edges of the same feature.

The `ResumeStrategy` / `ResumeKind` types and `[providers.resume]` TOML block are not meaningful without `--resume` parsing and the `run_repl` resume branch. On their own they would add dormant config surface, new validation failures, and no user-visible behavior. The reverse is also true: `--resume` without declarative provider resume syntax would force procedural provider branching, which would violate V1/V3. Those pieces should stay together.

The DB lookup stack is similarly coupled. The new `idx_session_turns_session_lookup` index is not meaningful by itself; it only exists to make the bare `session_id` query cheap under V8. `ProviderSessionMatch` and `find_provider_for_session()` are also not independently valuable unless something actually consumes the ordered matches. If you wanted the narrowest possible prerequisite split, the least-bad seam would be "index + helper" as substrate for resume, but that would be a prerequisite-only PR with no visible user value and immediate dependency from the real feature. I would not ask for that split.

Model-pool validation is not separable from lookup either. It is not a general validation concern; it is a guard on the specific provider selected by `find_provider_for_session()`. Without lookup there is nothing to validate. Likewise, the executor change to accept a resume payload is only meaningful because `run_repl` now resolves a provider, validates resumability, and composes the provider-specific argv. Splitting executor composition away from the caller would just create another dead internal surface.

The trace renderer extension also belongs in the same PR. Without the `"resumed"` write site, the new warning and `Resume target:` label are dead code. More importantly, once PR-F writes `update_session_capture(.., Some(id), "resumed")` pre-spawn, the trace change stops being optional polish and becomes part of the correctness story: it prevents trace from overstating what the runner knows after a failed attach. That is mutually load-bearing with the write.

The three helper functions (`should_emit_resume_short_line`, `should_emit_resume_detail_line`, plus the existing invocation-line helper pattern) are not separate concerns at all. They are local factoring added to make the stderr emission contract unit-testable. I would treat them as test-support structure inside the same concern, not split-worthy refactors.

Bottom line: I do not see multiple independently shippable concerns here. I see one feature that necessarily touches several layers, plus a few small factoring choices. If anything were split, only the DB substrate is even arguable, and I do not think V16 requires that split because it would trade one coherent review for a no-value prerequisite PR.
