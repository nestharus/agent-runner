# WU-11-01 — routing-fanout proposal

## Problem

WU-11-01 reduces a current routing risk on the supported multi-provider CLI path: traffic that users expect to be load-balanced can concentrate on one account even when sibling accounts are configured and available. The ticket names the user-visible symptom as 100%-to-one-provider routing for both `claude-opus` and `gpt-high` pools and requires the two reproduction harnesses to turn from RED to GREEN (`plans/tickets/phase-11/WU-11-01.md:16`-`plans/tickets/phase-11/WU-11-01.md:27`, `plans/tickets/phase-11/WU-11-01.md:44`-`plans/tickets/phase-11/WU-11-01.md:69` on branch `tickets/phase-11`).

RC-1 is **cached incomplete quota topology**. The RCA shows that `select_provider` refreshes only providers that `quota::is_stale` marks stale, and `is_stale` is provider-local: it checks the provider's own row, windows, and dynamic TTL, not sibling topology (`research/11-routing-fanout-rca.md:23`-`research/11-routing-fanout-rca.md:36`). The problem map narrows the current-state risk: a fresh one-window provider can stay fresh while siblings expose two windows because `is_stale` has no sibling comparison or peak-topology memory (`research/11-routing-fanout-problem-map.md:67`-`research/11-routing-fanout-problem-map.md:76`). Current code matches that map: `select_provider` calls `is_stale(state, &p.name)` before cached scoring (`src-tauri/src/balancer/mod.rs:98`-`src-tauri/src/balancer/mod.rs:126`), and `is_stale` only forces stale for missing rows, missing `refreshed_at`, zero windows, or TTL expiry (`src-tauri/src/quota/mod.rs:183`-`src-tauri/src/quota/mod.rs:217`). The current missing-window penalty also does not cover the low-used RC-1 shape because it only fires when a visible live window is at least `0.85` used (`src-tauri/src/balancer/mod.rs:12`-`src-tauri/src/balancer/mod.rs:20`, `src-tauri/src/balancer/mod.rs:288`-`src-tauri/src/balancer/mod.rs:295`).

RC-2 is **argmax concentration**. The RCA shows that learned-quota routing computes binding scores and returns a plain argmax, so a modest score gap pins all repeated selections to the higher-score provider until some outside state changes (`research/11-routing-fanout-rca.md:42`-`research/11-routing-fanout-rca.md:58`). The problem map identifies this as capacity-rank-and-pin behavior, not fanout (`research/11-routing-fanout-problem-map.md:69`-`research/11-routing-fanout-problem-map.md:72`). Current code matches: `score_by_density` filters learned eligible providers and returns `best_binding_score(&eligible).index` (`src-tauri/src/balancer/mod.rs:170`-`src-tauri/src/balancer/mod.rs:198`), while `best_binding_score` is a `max_by` over `binding_score` with no fanout or history term (`src-tauri/src/balancer/mod.rs:438`-`src-tauri/src/balancer/mod.rs:454`). The README documents this same contract as `pick = argmax` under "Load Balancing" (`README.md:228`-`README.md:236`).

## Design

Chosen option: two independent fixes. RC-1 gets a topology-aware refresh probe before density scoring. RC-2 gets deterministic score-band fanout inside learned density selection. Keeping them separate limits blast radius: topology repair changes quota freshness decisions, while fanout changes only the final learned-provider selector.

Fix 1, RC-1 topology-aware refresh:

- Algorithm change: keep the existing provider-local `quota::is_stale` behavior for normal TTL refresh, then add a pool-topology pass in `balancer::select_provider` when a `BalanceContext` is present. After the current normal refresh/session-scan loop, load cached windows for all model providers, compute each provider's live-window count, compute the pool expected count as `max(current live-window count, provider_quotas.topology_peak_live_window_count)` across the model's providers, and force a one-shot quota refresh for any provider whose live-window count is nonzero and below that expected count.
- Eligibility filter: only providers with a configured `quota_script` are topology-probed; providers without scripts already fall back to invocation-count behavior when windows are absent and should not be probed. Exhausted providers may still be refreshed before the later exhausted filter, preserving the existing behavior where a successful non-empty refresh clears `exhausted_at` before selection (`src-tauri/src/balancer/mod.rs:98`-`src-tauri/src/balancer/mod.rs:163`, `src-tauri/src/state/db.rs:1967`-`src-tauri/src/state/db.rs:1977`).
- Staleness detection: add `quota::is_topology_probe_due(state, provider_name, live_window_count, pool_expected_live_windows) -> bool`. It returns true when `live_window_count > 0`, `live_window_count < pool_expected_live_windows`, and `last_topology_probe_at` is missing or older than `TOPOLOGY_PROBE_COOLDOWN_SECS`. It does not replace `quota::is_stale`; `refresh_quotas` continues to call the provider-local `is_stale` contract.
- Policy constants: introduce `TOPOLOGY_PROBE_COOLDOWN_SECS = 60 * 60` in `quota::mod.rs`. One hour is the default because it is short enough to repair the RC-1 cached-topology miss on the next balanced invocation, but bounded so genuinely one-window providers in mixed-topology pools do not run a quota script on every invocation. Keep `HIDDEN_WINDOW_PENALTY_THRESHOLD = 0.85` unchanged to preserve the existing idle-provider guard (`src-tauri/src/balancer/mod.rs:932`-`src-tauri/src/balancer/mod.rs:963`).
- Data flow through `balancer::*`: `select_provider` still does normal stale refresh and session scan first. It then gathers quota/window state as it already does (`src-tauri/src/balancer/mod.rs:116`-`src-tauri/src/balancer/mod.rs:126`), computes topology expectations, probes under-count providers via `refresh_provider`, records `last_topology_probe_at`, reloads the probed providers' quota/window rows, and only then applies the existing exhausted filter and density/fallback branch (`src-tauri/src/balancer/mod.rs:127`-`src-tauri/src/balancer/mod.rs:168`).
- Data flow through `quota::*`: `refresh_provider` stays the script/auth-refresh/write entry point (`src-tauri/src/quota/mod.rs:114`-`src-tauri/src/quota/mod.rs:162`). `is_stale` remains provider-local. The new helper is additive and returns a boolean based on cached `QuotaRecord` topology metadata plus live-window counts supplied by `balancer`.
- Data flow through `state/db.rs`: `get_quota` returns the new topology metadata on `QuotaRecord`. `upsert_quota_refresh` updates `topology_peak_live_window_count` on every non-empty refresh to `max(previous_peak, new_live_window_count)`, while empty refreshes preserve prior windows and do not lower the peak (`src-tauri/src/state/db.rs:1900`-`src-tauri/src/state/db.rs:1944`, `src-tauri/src/state/db.rs:1967`-`src-tauri/src/state/db.rs:2039`). Add `record_topology_probe(provider_name)` to write `last_topology_probe_at` before or immediately after a topology-triggered refresh attempt, including failed attempts, so a persistently short provider does not thrash.
- Observability: when `select_provider` fires a topology probe and calls `record_topology_probe` because `live_window_count < pool_expected_live_window_count`, emit one deterministic `tracing::info!` event with fields `provider_name`, `live_window_count`, `pool_expected_live_window_count`, and `topology_peak_live_window_count`. Use `info` rather than `debug` because the user needs to verify in production traffic that the RC-1 repair path actually fired; the event is only emitted on the bounded probe branch, not on every selection. The event includes no wall-clock value, UUID, script output, path, token, or prompt text. Provider names are already user-visible in `refresh_quotas` IPC output (`src-tauri/src/lib.rs:297`-`src-tauri/src/lib.rs:303`, `src-tauri/src/lib.rs:344`-`src-tauri/src/lib.rs:390`).
- Determinism story: no randomness. Given the same DB rows, provider scripts, and current time relative to the cooldown, the probe set and subsequent selection are deterministic. Tests can seed `last_topology_probe_at` or leave it NULL.

Fix 2, RC-2 deterministic learned-score fanout:

- Algorithm change: replace `best_binding_score(&eligible).index` with a deterministic score-band selector, `select_binding_score_with_fanout(model, state, eligible)`. Compute `best_score = max(binding_score)`. If `best_score <= 0.0`, if any score is non-finite, or if fewer than two providers are inside the fanout band, preserve hard-pin argmax. Otherwise, build the fanout band from providers whose `binding_score >= best_score / FANOUT_SCORE_BAND_RATIO`.
- Fanout selection: within the band, choose the provider with the lowest lifetime invocation count from `state.get_provider(&model.name, &provider.name)`, then tie-break by higher binding score, then lower provider index. This uses the same provider-name aggregate already used by fallback scoring (`src-tauri/src/balancer/mod.rs:586`-`src-tauri/src/balancer/mod.rs:640`). The RC-2 harness records a successful invocation and increments quota ticks after each selection (`src-tauri/tests/routing_fanout_rca/rc2_argmax_concentration.rs:17`-`src-tauri/tests/routing_fanout_rca/rc2_argmax_concentration.rs:23`), so repeated selections create deterministic distribution pressure even though density projection itself ignores `calls_since_refresh` today (`research/11-routing-fanout-problem-map.md:71`-`research/11-routing-fanout-problem-map.md:72`).
- Policy constants: introduce `FANOUT_SCORE_BAND_RATIO = 2.0` in `balancer::mod.rs`. This directly encodes AC-2's "within ~2x" fanout requirement while preserving hard-pin behavior for wider gaps (`plans/tickets/phase-11/WU-11-01.md:53`-`plans/tickets/phase-11/WU-11-01.md:57` on branch `tickets/phase-11`). The boundary is intentionally exact: `2.5` would expand fanout beyond the ticket's stated "within ~2x" policy, while `1.9` could exclude a near-2x pair the AC says should fan out. Phase 6 implementation should sanity-check the RC-2 fixture's computed binding scores against this threshold rather than assuming projection rounding will land on the expected side. Use `FANOUT_SCORE_EPSILON = 1e-9` only for floating-point comparison stability if implementation needs it.
- Eligibility filter: keep the existing learned-density eligibility first: exhausted providers are filtered before scoring (`src-tauri/src/balancer/mod.rs:127`-`src-tauri/src/balancer/mod.rs:158`), recent-error providers get no binding score (`src-tauri/src/balancer/mod.rs:260`-`src-tauri/src/balancer/mod.rs:270`), and unlearned providers are excluded or trigger fallback (`src-tauri/src/balancer/mod.rs:184`-`src-tauri/src/balancer/mod.rs:195`, `src-tauri/src/balancer/mod.rs:321`-`src-tauri/src/balancer/mod.rs:328`). Fanout does not make unlearned, errored, zero-score, or exhausted providers eligible.
- Data flow through `balancer::*`: `score_by_density` still builds `ProviderEval`s from `compute_projections_from_records`; only the final line changes from plain argmax to score-band fanout. `score_by_invocation_count` and `round_robin_fallback` remain fallback-only and retain their existing provider-name lookups (`src-tauri/src/balancer/mod.rs:586`-`src-tauri/src/balancer/mod.rs:640`).
- Data flow through `quota::*`: none for RC-2. Quota windows and learned burn rates still feed binding scores through the current projection functions (`src-tauri/src/balancer/mod.rs:456`-`src-tauri/src/balancer/mod.rs:542`).
- Data flow through `state/db.rs`: fanout reads the existing `providers` aggregate through `get_provider`. It does not write new fanout state. The existing invocation finalization path updates aggregate counts, and the CLI path records selected provider identity before execution (`src-tauri/src/main.rs:2000`-`src-tauri/src/main.rs:2014`, `src-tauri/src/main.rs:2046`-`src-tauri/src/main.rs:2075`).
- Observability: when `select_binding_score_with_fanout` chooses a non-argmax provider because at least two providers are inside `FANOUT_SCORE_BAND_RATIO`, emit one deterministic `tracing::info!` event with fields `selected_provider_name`, `band_member_names`, `selected_invocation_count`, and `selected_binding_score`. Use `info` rather than `debug` because this branch explains the user-visible "why did it pick the lower score?" routing decision. Sort `band_member_names` by model provider order so the same fixture produces stable log content. The event includes no wall-clock value, UUID, prompt text, CLI args, or secrets; provider names are already part of model configuration and are exposed by `refresh_quotas` (`src-tauri/src/lib.rs:314`-`src-tauri/src/lib.rs:324`, `src-tauri/src/lib.rs:357`-`src-tauri/src/lib.rs:385`).
- Determinism story: no stochastic random fanout. The selector is pure over binding scores, existing aggregate counts, and provider order. Equal inputs produce equal selections; repeated successful selections fan out only because the supported invocation-write path updates provider-name counts.

Alternatives considered and rejected:

- Lower or remove `HIDDEN_WINDOW_PENALTY_THRESHOLD`. Rejected because the existing inline test documents the idle ChatGPT/Codex case where a low-used provider legitimately has only one visible window and should not be torpedoed (`src-tauri/src/balancer/mod.rs:932`-`src-tauri/src/balancer/mod.rs:963`).
- Pure peak-topology staleness without sibling-triggered probes. Rejected because legacy or pre-fix rows with a cached one-window topology have no known peak; the RC-1 reproduction seeds exactly that shape (`src-tauri/tests/routing_fanout_rca/rc1_incomplete_quota_topology.rs:14`-`src-tauri/tests/routing_fanout_rca/rc1_incomplete_quota_topology.rs:18`).
- Sibling-triggered refresh with no cooldown metadata. Rejected because a provider that genuinely and persistently exposes fewer windows than its siblings would run its quota script on every balanced invocation.
- Weighted or stochastic fanout. Rejected by ticket anti-scope and because deterministic count-balanced selection is simpler to test and audit (`plans/tickets/phase-11/WU-11-01.md:112`-`plans/tickets/phase-11/WU-11-01.md:123` on branch `tickets/phase-11`).
- A combined "fanout-aware density scorer" that folds missing-window penalties and provider-count pressure into one score. Rejected because it would entangle two independent root causes and make AC-1 regressions harder to separate from AC-2 policy.

## Schema and migration

This proposal adds topology metadata to `provider_quotas`. Current schema has no topology peak/hash metadata (`research/11-routing-fanout-problem-map.md:27`-`research/11-routing-fanout-problem-map.md:32`), and current `provider_quotas` only stores provider name, legacy used/reset fields, call count, refresh timestamps, empty-refresh timestamp, and exhaustion timestamp (`src-tauri/src/state/db.rs:520`-`src-tauri/src/state/db.rs:528`). The post-fix table shape is:

```sql
CREATE TABLE IF NOT EXISTS provider_quotas (
    provider_name TEXT PRIMARY KEY,
    used_percent REAL NOT NULL DEFAULT 0,
    resets_at TEXT,
    calls_since_refresh INTEGER NOT NULL DEFAULT 0,
    refreshed_at TEXT,
    last_empty_refresh_at TEXT,
    exhausted_at TEXT NULL,
    topology_peak_live_window_count INTEGER NOT NULL DEFAULT 0,
    last_topology_probe_at TEXT
);
```

`provider_quota_windows` remains shape-compatible with the current table: `provider_name`, `window_id`, `used_percent`, `resets_at`, `last_delta_percent`, `last_delta_calls`, primary key `(provider_name, window_id)` (`src-tauri/src/state/db.rs:530`-`src-tauri/src/state/db.rs:538`).

Migration helper: add `StateDb::ensure_provider_quotas_topology_schema(conn: &Connection) -> Result<(), String>`. It slots in `StateDb::open` immediately after the existing `ensure_provider_quotas_schema(&conn)` call and before `ensure_provider_quota_windows_schema(&conn)` (`src-tauri/src/state/db.rs:666`-`src-tauri/src/state/db.rs:668`). New DBs include the columns in the `CREATE TABLE IF NOT EXISTS provider_quotas` block; legacy DBs get:

```sql
ALTER TABLE provider_quotas
  ADD COLUMN topology_peak_live_window_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE provider_quotas
  ADD COLUMN last_topology_probe_at TEXT;
```

Legacy row population: after adding the columns, backfill `topology_peak_live_window_count` from the current cached windows:

```sql
UPDATE provider_quotas
SET topology_peak_live_window_count = (
    SELECT COUNT(*)
    FROM provider_quota_windows
    WHERE provider_quota_windows.provider_name = provider_quotas.provider_name
);
```

The migration does not synthesize historical peaks that are not present in the cache; the sibling-triggered probe covers that gap for pre-fix one-window rows. `last_topology_probe_at` remains NULL for legacy rows so the first observed topology mismatch is eligible for an immediate probe.

No schema change is required for RC-2 fanout because it reuses the existing provider aggregate read path (`src-tauri/src/balancer/mod.rs:599`-`src-tauri/src/balancer/mod.rs:607`, `src-tauri/src/balancer/mod.rs:626`-`src-tauri/src/balancer/mod.rs:637`) and the existing invocation finalization/write path (`src-tauri/src/main.rs:2008`-`src-tauri/src/main.rs:2014`, `src-tauri/src/main.rs:2067`-`src-tauri/src/main.rs:2075`).

## Supported-surface track

Deployment mode: single-user Tauri desktop app plus CLI runner, with local-only SQLite state opened through `StateDb::open`. The current DB open path creates and migrates tables in-process (`src-tauri/src/state/db.rs:503`-`src-tauri/src/state/db.rs:673`).

Customer cohort: the sole user/developer running local multi-provider pools. The directly affected cohort is any configured model with more than one provider account where quota scripts expose rolling-window data and learned density scoring is available.

Adjacent public or user-reachable paths and blast radius:

- `run_with_balancing` is the primary CLI path. It opens state, loads providers/sessions config, builds `BalanceContext`, calls `select_provider`, starts/finalizes invocation rows, marks quota exhaustion, ingests session turns, and increments quota ticks (`src-tauri/src/main.rs:1967`-`src-tauri/src/main.rs:2101`). Both topology probing and fanout affect this path.
- The interactive CLI path also constructs `BalanceContext` and calls `select_provider` before provider execution (`src-tauri/src/main.rs:1582`-`src-tauri/src/main.rs:1649`). It shares topology probing and learned selector behavior.
- `refresh_quotas` is adjacent because it calls `quota::is_stale`, `refresh_provider`, and reads/writes the same quota cache (`src-tauri/src/lib.rs:305`-`src-tauri/src/lib.rs:385`). Its response shape does not change, and it does not use the new sibling-aware topology probe because that probe is a routing-time pool decision.
- `README.md` §Load Balancing is user-reachable documentation and must be updated to describe topology probing, deterministic score-band fanout, preserved hard-pin behavior, and unchanged unit semantics (`plans/tickets/phase-11/WU-11-01.md:66`-`plans/tickets/phase-11/WU-11-01.md:68` on branch `tickets/phase-11`; `README.md:228`-`README.md:246`).
- `main.rs` consumers of balancer outputs still receive a provider index; no caller-facing return type changes are proposed (`src-tauri/src/main.rs:2000`-`src-tauri/src/main.rs:2003`).
- `lib.rs::test_model_with_db_path` calls `select_provider` with `None` for `BalanceContext`; because the new topology probe is gated on `BalanceContext` presence, this cached-only test path remains unchanged (`src-tauri/src/lib.rs:495`-`src-tauri/src/lib.rs:505`; `src-tauri/src/balancer/mod.rs:76`-`src-tauri/src/balancer/mod.rs:82`, `src-tauri/src/balancer/mod.rs:88`-`src-tauri/src/balancer/mod.rs:114`).
- The `state/db.rs` learning loop still uses `upsert_quota_refresh` for refresh-time window replacement and assistant-turn delta learning; the only new interaction is updating `topology_peak_live_window_count` on non-empty refresh, while empty refreshes do not lower the peak (`src-tauri/src/state/db.rs:1885`-`src-tauri/src/state/db.rs:2039`; test-intent row below for `upsert_quota_refresh_updates_topology_peak_without_lowering_on_shrink`).
- Session-turn ingestion remains unchanged. Density projection still reads assistant turns since each provider's `refreshed_at` (`src-tauri/src/balancer/mod.rs:272`-`src-tauri/src/balancer/mod.rs:282`), and this proposal adds no schema or read-path change to session-turn ingestion.

Migration path: forward-only through `StateDb::open`. New DBs create the post-fix `provider_quotas` shape. Existing DBs add the two topology columns through `ensure_provider_quotas_topology_schema` after the current quota-table creation block and existing quota schema helper. Legacy rows are populated from cached `provider_quota_windows` counts, and NULL `last_topology_probe_at` allows one immediate topology repair probe when a mismatch is observed.

Rollback path: rollback is `git revert` of the WU-11-01 PR plus, if needed, restoring a pre-migration SQLite backup. Because the schema change is additive, legacy quota rows and window rows survive a downgrade as data, and the current old code uses explicit column names for its normal quota reads/writes. That is not a compatibility shim or a supported downgrade guarantee; the project convention remains forward-only, and a backup restore is the clean rollback for state.

Observability: no new metrics and no IPC response changes. Add deterministic `tracing::info!` events for the two new runtime branches: topology-probe fired and fanout-selected. The topology-probe event fields are `provider_name`, `live_window_count`, `pool_expected_live_window_count`, and `topology_peak_live_window_count`. The fanout-selected event fields are `selected_provider_name`, `band_member_names`, `selected_invocation_count`, and `selected_binding_score`. These logs contain no secrets, no wall-clock fields, no UUIDs, and no fixture-varying data beyond deterministic provider names, counts, and scores. Provider names are already user-visible through model/pool configuration and `refresh_quotas` output (`src-tauri/src/lib.rs:297`-`src-tauri/src/lib.rs:303`, `src-tauri/src/lib.rs:314`-`src-tauri/src/lib.rs:324`). The other observable signals are local SQLite state and existing invocation history: `provider_quotas.topology_peak_live_window_count`, `provider_quotas.last_topology_probe_at`, `provider_quota_windows` row counts, and the per-provider `invocations`/`providers` histogram. README should mention that `quota_check` remains the diagnostic way to inspect refreshed windows and picks (`README.md:696`-`README.md:700`).

## Assumption register

1. Provider-name identity remains the supported account identity for routing state. Evidence: quota records are documented and stored by provider name (`src-tauri/src/state/db.rs:137`-`src-tauri/src/state/db.rs:148`), and README says provider state is keyed by provider `name` (`README.md:244`-`README.md:246`). Invalidated if a supported config intentionally has multiple distinct accounts with the same provider name and needs separate quota/fanout state.
2. A provider in the same model pool that exposes fewer live windows than its siblings is suspicious enough to probe once per cooldown, not to penalize blindly. ## Qualitative net-value statement

Yes. This proposal clearly reduces a concrete current-state risk on the current supported surface: multi-provider CLI routing can currently keep a stale incomplete quota topology fresh and can pin learned selections to a single argmax provider. That risk is documented in the problem map's `Already-risky or brittle behavior` and `Supported and user-reachable paths through the surface` fields (`research/11-routing-fanout-problem-map.md:67`-`research/11-routing-fanout-problem-map.md:102`) and reproduced by the two RED harnesses (`src-tauri/tests/routing_fanout_rca/rc1_incomplete_quota_topology.rs:10`-`src-tauri/tests/routing_fanout_rca/rc1_incomplete_quota_topology.rs:34`, `src-tauri/tests/routing_fanout_rca/rc2_argmax_concentration.rs:10`-`src-tauri/tests/routing_fanout_rca/rc2_argmax_concentration.rs:29`).

The risk reduction outweighs the added blast radius, migration, and rollback burden. The blast radius is bounded to the problem map's `Adjacent surfaces inside the blast radius` and `Supported and user-reachable paths` fields: `select_provider`, `refresh_provider`/quota cache writes, `refresh_quotas` as an adjacent writer, and the two CLI invocation paths (`research/11-routing-fanout-problem-map.md:81`-`research/11-routing-fanout-problem-map.md:102`). The migration cost is an additive local SQLite schema change under the existing `ensure_*_schema` pattern, and rollback is a normal PR revert plus DB backup restore if state rollback is required. The result is a smaller current-state routing risk with a controlled schema addition and deterministic, testable behavior.
